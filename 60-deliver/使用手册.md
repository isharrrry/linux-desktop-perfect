# 使用手册

> **本仓的总使用手册**：装什么、怎么跑、对着需求怎么验、跑不通怎么办。
> 覆盖两条使用路径——**自己的源码工程重编**（需求规定的正常用法，REQ-FN-001/002）与
> **Windows 上已编好的程序集免编运行**（实测扩展，§4.4 与 §7）。
> 每条结论带实测读数或明确出处；凭推断的地方标「推断」。
> 需求侧事实源是 [《需求与验收判据文档》](../20-spec/需求与验收判据文档.md) §4/§9，判据入口见
> [`50-verify/index/索引表.md`](../50-verify/index/索引表.md)。

> **读者按用途跳转**：只想跑起来 → §0、§4；首次部署 → §2–§3；
> 想知道某条需求怎么验 → §5；跑不通 → §8。

## 0. 三十秒速查

最常用的一条路（WPF 程序，本机已装好运行时）：

```bash
D=~/.local/share/ldp/dotnet
env -i DISPLAY=:91 HOME=$HOME DOTNET_ReadyToRun=0 $D/dotnet /path/to/App.dll
```

三件事记牢：

1. **只拷三个文件**：`App.dll` + `App.deps.json` + `App.runtimeconfig.json`（同一目录）。
2. **唯一硬需求是 `DOTNET_ReadyToRun=0`**（D-005）。
3. **前提是运行时已装好**——仓库里没有任何二进制产物与上游快照，见 §2–§3。

---

## 1. 全景：四段

| 段 | 什么时候做 | 输入 | 产出 | 能否跳过 |
|---|---|---|---|---|
| **A 备料** | 首次，一次 | 仓库外的 4 样文件 + 系统依赖 | 构建链的输入就位 | **不能**（仓库里没有） |
| **B 构建** | 首次，一次 | A 段产出 | `~/.local/share/ldp/dotnet`（约 70 MB） | 可以——直接拷别人装好的整个目录 |
| **C 运行** | 每次跑程序 | B 段产出 + 三件套 | 窗口 + 可选 UIA 树 | **不能** |
| **D 自检** | 出问题时 | 已装运行时 | 判据读数 | 可跳过（但「没崩」不等于通过） |

A 变一次 B 要重来；B 变一次 C 不用改。

## 2. A 段：备料

### 2.1 四样不在仓库里的输入

仓库用 `.gitignore` 排除了所有二进制产物（`40-build/**/bin/`、`40-build/pack/out/`）与上游快照
（`SNAPSHOT.json` 里 `tracked_in_git: false`），所以下面四样必须自己取：

| # | 干什么（大白话） | 输入 | 输出 | 有无替代 |
|---|---|---|---|---|
| A1 | 把微软 WPF 官方源码整包搬到固定目录 | 网络（gitee 镜像；GitHub 直连本机不通），161 MB | `40-build/upstream/wpf/`（7380 文件 / 4538 个 `.cs`） | 从本地前身仓 `WPFOnLinux` 的 `a9141483e` 导出（见 `SNAPSHOT.json` 的 `extract_command`）；或直接拷别人这个目录。**无实质替代** |
| A2 | 下载微软 Windows 版桌面运行时包（当素材） | 能访问 nuget.org | `40-build/lock/packs/microsoft.windowsdesktop.app.runtime.win-x64.10.0.11.nupkg`（39 MB） | 向别人拷这份文件；或从 `~/.nuget/packages` 缓存找。缺了打包步骤报 `LDP-E-PACK-205` 退出 |
| A3 | 引用程序集包（编译期用） | 做过一次 NuGet 还原 | `…ref.10.0.11.nupkg`（7.6 MB） | 打包脚本发现缺失会**自动从缓存生成**——基本不用管 |
| A4 | 造 3 个空壳包，顶替连不上的私有源 | A3 已就位 | `40-build/lock/offline-feed/*.nupkg` | 私有源能连通就不用；本机不通，所以必需 |

取件命令见 `40-build/lock/README.md`；A1 的来源与 sha 见 `40-build/upstream/wpf/SNAPSHOT.json`。

**为什么 A1 特别容易踩**：`apply.mjs` 只检查 `40-build/upstream/wpf` **目录存在**，不报「快照没取」——
空快照会一路错到编译阶段。取完后先自检：

```bash
find 40-build/upstream/wpf -name '*.cs' | wc -l    # 期望 ≈ 4538
```

### 2.2 系统依赖

| 用途 | 需要什么 | 缺了会怎样 |
|---|---|---|
| 编译原生件 | `gcc`、`make`、`libx11-dev`、`zlib1g-dev` | `libwpfwin32.so` 编不出来，B 段第 ② 步失败 |
| 解包 | `unzip` | `install-runtime` 解 nupkg 失败 |
| 显示 | X11：真桌面或 `Xvfb` | 程序起来但没窗口 |
| 验证脚本 | `openbox`、`wmctrl`、`xdotool`、ImageMagick 的 `import` | 验证器找不到窗口 / 截不了图 |
| 文本与字体 | `libharfbuzz`、`libfreetype`、`libfontconfig`、ICU | 起不来或全是方块字 |
| 图像 | `liblcms2`、`libtiff`、`libSkiaSharp.so`（随 AOT 发布带出） | 图像解码不通 |
| 运行时 | .NET SDK `10.0.401`（`40-build/global.json` 锁定）+ .NET 10 运行时 | 编不了 / 加载不了框架 |

`libgdiplus` 是 [《已知坑与降级清单》](../70-operate/已知坑清单.md) 里唯一明写「必须 `apt install`」的项。

### 2.3 备料自检

```bash
node 50-verify/env/probe-env.mjs      # 依赖矩阵读数（任一项缺会让所有判据一起红）
```

## 3. B 段：构建 7 步（顺序不能换）

### 3.1 总表

| # | 干什么（大白话） | 输入 | 输出 | 有无替代 |
|---|---|---|---|---|
| ① | 把只读的上游源码复制成「可改的树」，顺手把 `net10.0-windows` 改 `net10.0` | A1 | `40-build/build/wpf/`（约 7000 文件，**每次全删重建**） | 无 |
| ② | 编译 5 个 C 写的库 | 五个原生件的源 + 头文件 | `40-build/*/bin/*.so` | 只有 `native-shim` **必需**；其余可缺，打包会记「原生件待补」，对应功能不可用 |
| ③ | 把 WPF 重新编译成 26 个自产 dll | ① + ② + 联网（SkiaSharp 2.88.9） | `40-build/wpf-port/out/*.dll` | 无 |
| ④ | 把 ③ 的 dll、② 的 so、上游剩余件组装成两个安装包 | ③ + A2 | `40-build/pack/out/` 两个 nupkg | 无 |
| ⑤ | 把包解成「用户目录下的假 dotnet 根」 | ④ + 系统 dotnet | `~/.local/share/ldp/dotnet/`（61 dll / 4 so / `env.sh` / manifest） | **有**：拷别人装好的整个目录 |
| ⑥ | 把渲染桥编成 `wpfgfx_cor3.so` 装进框架，顺带 `libSkiaSharp.so` | ⑤ 已装 + NativeAOT 工具链 | `$FX/wpfgfx_cor3.so`（约 5 MB） | 无。**必须排在 ⑤ 之后**（⑤ 会删框架目录，K-003） |
| ⑦ | 把 ② 的 so 拷到框架根，建 Win32 同名软链 | ② + ⑤ | `$FX/*.so` + 12 条软链 | 可手工 `cp`，但漏一次整条链路就不可用（K-231） |

`$FX` = `~/.local/share/ldp/dotnet/shared/Microsoft.WindowsDesktop.App/10.0.11`。

### 3.2 每步细节

**① 派生树**

```bash
node 40-build/appliers/apply.mjs
node 40-build/appliers/apply.mjs --check    # 只校验是否与上游+补丁一致
```

改动是确定性文本替换（TFM、P/Invoke 目标名、构建排除）。它 `fs.rmSync` 重建目标目录，
**任何手改都会被覆盖**——补丁只写在 applier 里（ADR-002）。它同时自动补建
`PresentationBuildTasks`（K-002），所以不必手工补。

**② 原生件**

```bash
make -C 40-build/native-shim
make -C 40-build/wic-dwrite
make -C 40-build/text-stack
make -C 40-build/zlib-native
make -C 40-build/media-bridge
```

`text-stack` 的头文件用 `make -C 40-build/text-stack headers` 联网取（不入库）；
缺 `libx11-dev` 时 `build-shim.sh` 会直接给出 Debian/Ubuntu 与 RHEL 的包名。
各目录的 `make` 还会额外产出探针（`clip-probe`、`dwp-probe`、`wic-probe` 等），判据要用。

**③ 移植链**

```bash
node 40-build/wpf-port/build-port.mjs --map      # 构建 + 映射到派生树 artifacts/bin
node 40-build/wpf-port/build-port.mjs --list     # 只打印依赖序
node 40-build/wpf-port/build-port.mjs --only System.Xaml
```

不带 `--map` 只编译不映射，④ 会拿不到产物。读数落 `40-build/wpf-port/build-report.json`。

**④ 打包**

```bash
node 40-build/pack/build-pack.mjs
```

不联网；缺 A2 直接 `LDP-E-PACK-205` 退出。产物：Ref 包 + `Runtime.linux-x64` 包，
组装报告在 `40-build/pack/pack-report.json`（含自产件替换数与原生件清单）。

**⑤ 安装**

```bash
node 40-build/pack/install-runtime.mjs                                   # 装/更新
node 40-build/pack/install-runtime.mjs --check                            # 只检查
node 40-build/pack/install-runtime.mjs --ver 10.0.11 --root ~/ldp-dotnet  # 换版本/换根
node 40-build/pack/install-runtime.mjs --smoke                            # 起 Xvfb 跑启动阶段读数
```

注意 `--check` 也会先查 ④ 的 nupkg，没打包时会报 `LDP-E-PACK-205`。
它**先删整个框架目录再解包**，所以 ⑥ 必须后跑。生成的 `env.sh` 含 `DOTNET_ROOT`、`PATH`、
`LD_LIBRARY_PATH`、`DOTNET_ReadyToRun=0`、`WPF_LINUX_WIN32_SHIM`，末尾还有一句 `unset DISPLAY`。

**⑥ 渲染桥**

```bash
node 40-build/milcore-bridge/build-bridge.mjs --install ~/.local/share/ldp/dotnet
node 40-build/milcore-bridge/build-bridge.mjs --check
```

它同时把 AOT 发布目录里的 `libSkiaSharp.so` 带进框架根——少了它 `FontFamily` 初始化就崩。
读数见 `40-build/milcore-bridge/bridge-report.json`。

**⑦ shim 部署**

```bash
sh 40-build/install-shims.sh           # 装
sh 40-build/install-shims.sh --check   # 只检查
```

装 3 个 `.so` 到 `$FX` 根，并建 `USER32.dll → libwpfwin32.so` 之类 12 条软链（大小写各一份）。
`--check` 仍要求 ② 的产物存在，否则 `exit 1`。

### 3.3 构建后的自检

```bash
node 40-build/pack/install-runtime.mjs --check     # 框架件/deps.json/runtimeTarget 三项
sh 40-build/install-shims.sh --check               # 三个 .so + 别名链接
node 40-build/milcore-bridge/build-bridge.mjs --check
```

## 4. C 段：运行

### 4.1 总表

| # | 干什么（大白话） | 输入 | 输出 | 有无替代 |
|---|---|---|---|---|
| ⑧ | 只拷三个文件到同一目录 | Windows 上 `dotnet build -c Release` 的输出 | Linux 上的三件套 | 无。**不要**拷 Windows 侧 `publish` 出来的 WPF 框架件（推断：会与自产框架冲突）|
| ⑨ | 准备一块显示 | `Xvfb` 或真桌面 | 一个 `DISPLAY` | 真桌面、`ssh -X`、Xephyr 都行 |
| ⑩ | 带环境变量启动 | 三件套 + ⑨ + B 段产出 | 窗口 | `source env.sh` 也行，但它会 `unset DISPLAY`，要自己补 |
| ⑪ | 确认真的出画面 | ⑩ 已运行 | 截图 + UIA 树 + 判定读数 | 手工 `xdotool` + `import`；**只看进程不崩不算通过** |

### 4.2 拷什么

| 拷 | 不拷 |
|---|---|
| `App.dll` | `App.exe`（Linux 不用 apphost） |
| `App.deps.json` | `App.pdb` |
| `App.runtimeconfig.json` | `runtimes/win-*/` 下的原生件 |
| 自己引用的第三方 dll | Windows `publish` 出来的 WPF 框架件 |

### 4.3 显示

```bash
Xvfb :91 -screen 0 1280x1024x24 &
```

要做窗口查找类判据时还需要窗口管理器（`openbox &`），否则 `wmctrl -l` 为空。

### 4.4 启动

**最省事的方式：用本仓的启动器（推荐）**

```bash
bash 70-operate/启动器/sourcetree /path/to/your/app.exe
```

它做了四件事：
1. **自动带好全部环境变量**（`DOTNET_ROOT` / `DOTNET_ReadyToRun` / `LD_LIBRARY_PATH` / `WPF_LINUX_WIN32_SHIM` / **`WPF_LINUX_ATSPI=0`** / `DISPLAY` 默认 `:303`）；
2. **检测 `.lnk` 快捷方式并明确报错**（`exit 2`，不再静默失败，K-1310）；
3. **`cd` 到应用目录**（`ST_APP` 可覆盖，默认 `/tmp/stpkg/SourceTree/app-3.4.15`）；
4. **检查应用可执行文件存在**（不存在则 `exit 3`）。

> **⚠️ `WPF_LINUX_ATSPI=0` 是必需的（K-1379）**：缺了它，AT-SPI 初始化会阻塞 WPF UI 线程，
> **SourceTree 启动后窗口根本不出现**（用户看到的就是「白屏」）。
> 实测对照：不带该变量 ⇒ `:10` 上无 SourceTree 窗口；带上 ⇒ 窗口正常（截图 228310B / 2077 色）。

**启动 SourceTree（本仓的主目标）**：

```bash
cp 70-operate/启动器/sourcetree /tmp/stpkg/SourceTree/app-3.4.15/sourcetree
chmod +x /tmp/stpkg/SourceTree/app-3.4.15/sourcetree
DISPLAY=:303 /tmp/stpkg/SourceTree/app-3.4.15/sourcetree >/tmp/st.log 2>&1 &
```

**启动后验证环境是否正常**：

```bash
bash 70-operate/启动器/verify-inotify-fix.sh
```

（该脚本检查 inotify 上限、启动 SourceTree、确认 `RepoWatcher` 无报错，K-1311。）

> **⚠️ 注意**：`RepoWatcher` 无报错**不代表**「暂存」可用 —— K-1333 已实测否定该假设（真因是 `Tabs.Count=0`）。脚本仅作**环境自检**。

**手动方式（启动器内部就是这些）：**

**外部程序集（Windows 编译的）**：

```bash
D=~/.local/share/ldp/dotnet
env -i DISPLAY=:91 HOME=$HOME DOTNET_ReadyToRun=0 $D/dotnet /path/to/App.dll
```

**自己的源码工程（需求规定的正常用法）**：

```bash
# 1) 只改 TargetFramework（不改工程文件其它地方，REQ-FN-002）
#    net10.0-windows → net10.0
# 2) 用自产 pack 构建
dotnet build -c Release
# 3) 用同一套环境启动
env -i DISPLAY=:91 HOME=$HOME DOTNET_ReadyToRun=0 $D/dotnet ./bin/Release/net10.0/App.dll
```

**要看 UIA 结构树**（判据用）再加三个：

```bash
FX=$D/shared/Microsoft.WindowsDesktop.App/10.0.11
DOTNET_STARTUP_HOOKS=$FX/LdpA11y.dll LDP_A11Y_DUMP=/tmp/tree.json LDP_A11Y_REPEAT=1
```

`LDP_A11Y_REPEAT=1` 时树文件每 400 ms 被整体重写，读的时候要重试（K-013 记录过读到半截）。

## 5. 对着需求：每条 REQ 怎么用、怎么验

需求一共 30 条（REQ-FN-001~030），分 8 组。下表给出「你在使用中会碰到什么」与「对应判据的单行命令」——
命令与 [`50-verify/index/索引表.md`](../50-verify/index/索引表.md) 一致，读数落 `50-verify/读数/ACC-xxx/`。
当前状态以 [《需求与验收判据文档》](../20-spec/需求与验收判据文档.md) §9 与实测读数为准（两者不一致时以读数为准并回写文档）。

### 5.1 构建与框架（REQ-FN-001~005）

| REQ | 使用中会碰到什么 | 判据命令 |
|---|---|---|
| REQ-FN-001 应用源码在 Linux 重编 | 只改 `TargetFramework` 后 `dotnet build -c Release` 应 0 error | `node 50-verify/build/build-sample.mjs` |
| REQ-FN-002 不改工程文件解析到自产 pack | 保留 `<UseWPF>true</UseWPF>`，构建日志里 `FrameworkReference` 命中自产 pack | `node 50-verify/build/build-sample.mjs --log` |

## 6. 环境变量：到底要几个

### 6.1 结论表

| 变量 | 是否必需 | 依据 |
|---|---|---|
| `DOTNET_ReadyToRun=0` | **必需** | 上游 pack 件是 win-x64 ReadyToRun，Linux 加载即 `BadImageFormatException`（D-005） |
| `DISPLAY` | **必需** | 没有它连不上 X |
| `DOTNET_ROOT` | 不必需 | 用绝对路径 `$D/dotnet` 时宿主按自身位置找框架；用系统 `dotnet` 时设了也不管用 |
| `WPF_LINUX_WIN32_SHIM` | 不必需 | resolver 顺序是 环境变量 → 应用目录 → 程序集目录；`install-runtime` 已把 shim 放进框架根 |
| `LD_LIBRARY_PATH` | 不必需 | 文本/媒体/图像三类样本各做「有/无」对照共 6 次，结果一致 |
| `DOTNET_STARTUP_HOOKS` + `LDP_A11Y_DUMP` | 只有要 UIA 树时 | 只影响读数；`LDP_A11Y_DUMP` 没有默认值 |

### 6.2 实测记录（2026-11-01）

| 实验 | 命令 | 结果 |
|---|---|---|
| 全空环境 | `env -i DISPLAY=:77 HOME=$HOME $D/dotnet WinApp.dll` | `BadImageFormatException at Application.ApplicationInit`，进程 abort |
| 只加一个 | 同上 + `DOTNET_ReadyToRun=0` | 窗口 5 个、进程存活 |
| 系统 host | `/usr/bin/dotnet` + `DOTNET_ROOT=$D` | `You must install or update .NET` |
| WinForms | 最小集跑外部 WinForms 程序 | 窗口 1 个、4 个非致命异常、存活 |
| 写进 json | `configProperties` 试 `System.Runtime.ReadyToRun` 等 4 种键名 | **全部无效**，仍抛同一个异常 |
| 钩子写进 json | `configProperties` 加 `System.StartupHook` | 树未生成（同程序用环境变量方式出 4 节点） |

结论：`DOTNET_ReadyToRun=0` **省不掉**，只能靠环境变量或 wrapper 脚本。
想彻底免掉，只能把上游 ReadyToRun 件全部换成纯 IL 自产件（即「全部件自产」路线）。

## 7. WPF 与 WinForms 的差别

**安装阶段没有任何差别**：WinForms 的 `System.Windows.Forms.dll`（13.7 MB 官方原版）与
`System.Drawing.Common.dll` 就在同一个框架包里，`build-port`/`build-pack` 的工程列表里没有
WinForms 工程。Windows 上编译的 WinForms 程序，`runtimeconfig.json` 同样引用
`Microsoft.WindowsDesktop.App 10.0.0`。

**运行阶段有两处差别**：

| 差别 | 说明 | 依据 |
|---|---|---|
| 软链 | WinForms **必须有** `$FX` 下的 Win32 同名软链。移走软链实测：WPF 照常出窗口 5 个，WinForms 直接 `DllNotFoundException` | K-014：WinForms 的 CsWin32 生成码用 `[LibraryImport]`，`SetDllImportResolver` 对它不生效 |
| 深度 | WinForms 能启动、建窗、控件位置正确，但 `System.Drawing` 自绘抛 `EntryPointNotFoundException @ IGraphicsContextInfo.GetHdc` | K-249/K-250；双缓冲 `RenderInternal` 在 Unix 后端直接 `throw new NotImplementedException()` |

## 8. 失败对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| `BadImageFormatException at ApplicationInit` | 没关 R2R | 加 `DOTNET_ReadyToRun=0` |
| `DllNotFoundException: USER32.dll`（WinForms） | 框架目录缺 Win32 软链 | `sh 40-build/install-shims.sh` |
| `You must install or update .NET` | 用了系统 `dotnet`；或跨 major | 用 `$D/dotnet`；.NET 6/8 编译的加 `--roll-forward Major` |
| 进程在但没窗口 | 没有 X；或 `env.sh` 把 `DISPLAY` 清掉了 | 起 Xvfb；`unset DISPLAY` 后重新 `export` |
| `LDP-E-PACK-205` | 缺 Runtime pack nupkg | 按 `40-build/lock/README.md` 取件 |
| 编译期找不到 `PresentationBuildTasks` | 派生树被重建过 | 重跑 `apply.mjs`（自动补建） |
| 窗口找得到但判据判「失败」 | 可能是匹配到了 WPF 内部窗口 | 以 UIA 树节点数为准（K-248） |
| 树文件读到 `Unexpected end of JSON` | `LDP_A11Y_REPEAT=1` 正在重写 | 带重试地读，且检查末尾是否 `}` |

## 9. 明确做不到的

| 做不到 | 性质 | 依据 |
|---|---|---|
| 跑 self-contained / 单文件 `win-x64` 发布 | **推断**：那类输出带 Windows 原生件 | 未登记、未实测 |
| 跑 .NET Framework（`net48` 等）程序集 | 不是同一个运行时 | — |
| WinForms 的自绘与双缓冲 | 缺 GDI 设备上下文语义 | K-249/K-250、D-025 |
| 依赖第三方原生 dll 的库 | shim 只覆盖清单内函数（WinForms 专项需 410 个，现覆盖 103） | D-025 |
| 打印、媒体播放、输入法 | 判据红或降级 | ACC-024、ACC-022、ACC-017 |
| Windows 宿主身份仿真 / PE 加载 | 明确非目标 | ADR-001 |
