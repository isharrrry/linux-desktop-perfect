## ⚠️ 遗留：`/tmp/wfout/WfApp.dll` 的「渲染」未达成（K-143）

**目标原文那句是「Windows 编译的 `/tmp/wfout/WfApp.dll` 能启动 + 渲染 + 点击」。经实测，只达成了前 1/3：**

| 验收点 | 状态 | 证据 |
|---|---|---|
| **启动** | ✅ | 程序集加载、WPF/控件初始化、消息循环全部正常 |
| **窗口** | ✅ | `xdotool search` 得到 `10485762`，`xwininfo` 显示 `784x560` + `IsViewable` |
| **控件** | ✅ | 日志里 `CreateWindowExW title=btn size=100x30 parent=0xa00002` |
| **`WM_PAINT` 链路** | ✅ | 加诊断后 `[PAINT] BeginPaint` 被调 **18 次** |
| **渲染（画面出现）** | ❌ | 截图恒为 377 字节空白 |

**根因（已定位，非猜测）**：shim 里**所有**"给 HDC"的函数都返回同一个假值 `WPF_FAKE_DC`：
```c
HDC GetDC(HWND h)               { return WPF_FAKE_DC; }
HDC GetWindowDC(HWND h)         { return WPF_FAKE_DC; }
HDC CreateCompatibleDC(HDC hdc) { return WPF_FAKE_DC; }
BOOL BeginPaint(...)            { ps->hdc = WPF_FAKE_DC; ... }
```
标准 WinForms 控件的绘制走 `Graphics.FromHdc(假 HDC)` ⇒ **画到内存，落不到 X11**。

**为什么 `ACC-028` 判据仍 PASS**：判据用的是本仓自产的 `samples/WinFormsBasics`，
它的 `Graphics` **走自编 `System.Drawing.Common` 的 X11 后端**（`Graphics.FromHwnd` 路径），
**确实画出来了**（K-114）。

**两条路径的真实差异**：

| 路径 | 状态 |
|---|---|
| `Graphics.FromHwnd(hwnd)`（自编 SDC 的 X11 后端） | ✅ |
| `Graphics.FromHdc(假 HDC)`（标准 WinForms 控件） | ❌ |

**2026-11-01 续做（K-142～K-149，六轮，每轮都有实测）**：

| 轮 | 做了什么 | 结论 |
|---|---|---|
| K-142 | `InvalidateRect`/`RedrawWindow` 改成合并投递 `WM_PAINT`；给 `BeginPaint` 加诊断 | `WM_PAINT` 链路通了，`BeginPaint` 被调 **20 次** |
| K-143 | 列出 shim 里所有"给 HDC"的函数 | 全部返回同一个假值 `WPF_FAKE_DC` |
| **K-144** | **新建 `win32_gdi_dc.{h,c}`（约 240 行）：真 HDC = X11 Window+GC；`FillRect`/`TextOutW`/`SetTextColor`/`SelectObject`/`CreateSolidBrush` 全部改成真画** | HDC 建出来了（`[GDI] wpf_hdc_get ... 784x560` ✓），但 **`FillRect` 0 次** |
| K-145 | 追到 `Graphics.FromHdc` → `GdipCreateFromHDC` → libgdiplus 不认识我们的 HDC | 找到"为什么 HDC 真了也不画" |
| **K-146** | **跨语言桥接：shim 导出 `wpf_hdc_hwnd`/`wpf_hdc_drawable`；SDC 的 `FromHdc` 认出 shim HDC 就转 `FromHwnd`（走 `GdipCreateFromXDrawable_linux`）** | 两侧都编译通过、符号已导出 |
| K-147 | SDC 的 `FromHdc` 加诊断 | **`FromHdc` 0 次** —— 不是入口 |
| **K-148** | `FromHdcInternal`（原来 `return null`）/`FromHwndInternal` 也加诊断并修 | **三个入口全是 0 次** —— WinForms 根本没创建 `Graphics` |
| K-149 | shim 的 `DefWindowProcW(WM_PAINT)` 改成用窗口类背景刷真填 | **`FillRect` 仍 0 次** —— 连 `DefWindowProc` 都没进 |

**最终判断（诚实）**：`WfApp` 的空白**卡在 `System.Windows.Forms.dll`（官方二进制）的内部策略上** ——
它在 `ControlStyles.UserPaint` 为 false 时**既不创建 `Graphics`、也不转 `DefWndProc`**，
而是把 `WM_PAINT` 直接吞掉。**shim 里再加绘制函数都不会被调到。**

**这一轮（2026-11-01）实际交付的东西**：
- `win32_gdi_dc.{h,c}`：一套**可用的真 HDC + GDI 绘制**（`FillRect`/`FrameRect`/`Line`/`TextOut`/颜色/选中对象），约 240 行；
- `Graphics.FromHdc` 的**跨语言桥接**（shim 两个导出 + SDC 一个分支 + try/catch 回落）；
- `WM_PAINT` 的**背景填充**（用 `WNDCLASS.hbrBackground`）；
- `InvalidateRect`/`RedrawWindow` 的**合并投递**（不再 no-op）；
- 全套**诊断开关**（`WPF_LINUX_KEY_DIAG` 下的 `[GDI]`/`[SDC]`/`[PAINT]` 日志）。

**如果以后要继续**：得反编译 `System.Windows.Forms.dll` 的 `Control.WmPaint`，
搞清楚它在什么条件下才创建 `Graphics` —— 这属于"改官方二进制行为"级别的工作。

## 与隔壁 `WPFOnLinux` 项目的做法对照（2026-10-31）

两个项目面对同一个问题（在 Linux 上跑 Windows 编译的 WPF/WinForms 程序），策略不同：

| 问题 | `WPFOnLinux` 的做法 | 本仓的做法 | 谁更合适 |
|---|---|---|---|
| **`user32.dll` 等 P/Invoke** | `SetDllImportResolver` + `[ModuleInitializer]`（与我们在 WPF 侧完全一致）| 同左 | **一致，无需改** |
| **第三方库自己 `[DllImport("gdiplus.dll")]`** | **实现 `gdiplus.dll` 的 44 个函数**，真解码转发到 Skia/WIC；只读族真做、写族如实失败 | 已导出 **29 个 `Gdip*`**（不足 44，但覆盖了图像读族）| **两边的方向相同**；我们应该补齐到 44 个（成本低）|
| **`System.Drawing.Common`（托管层）** | **原版借用**（`borrow/`，取自 RT 的 `refruntime/`，元数据不动 ⇒ 身份一致），**不重实现** | 也是原版 | **它没遇到我们的问题**：它不跑 WinForms，`System.Drawing.Common` 的托管层没被触发 |
| **WinForms 家族的 `System.Windows.Forms` 等** | 同样原版借用，**业务真用到才需要** | 原版（13.7 MB）| 同上 |

**关键差异**：`WPFOnLinux` 的**验收范围不含 WinForms**，所以它只需要 `gdiplus.dll` 这一层；
本仓的目标包含「WinForms 程序拷过来能跑」，于是**必然会撞上 `System.Drawing.Common` 的托管层硬检查**
（K-018：抢 resolver 会撞 `InvalidOperationException`，从外部绕不过去）。

**结合后的做法建议**（更符合本仓目的、也更好维护）：
1. **`user32/kernel32` 这层保持"符号链接 + resolver"双轨**：
   - WPF 走 resolver（现状，已 PASS）；
   - WinForms 的 CsWin32 走 `$FX/*.dll` 符号链接（实测 resolver 对 `[LibraryImport]` 不生效）。
   两条都留着不难维护，因为符号链接只是 `ln -sf`，而且**只对 WinForms 家族生效**（有 `SHIM-COVER` 日志可查）。
2. **`gdiplus` 面补齐到 44 个**，与隔壁对齐 —— 这是**共用的底层**，两边都在做，没必要各写一份。
3. **`System.Drawing.Common` 只能重编**（K-018），建议走「取开源实现改程序集名+重签名」，
   而不是"自己从零写" —— 因为它的 API 面是 WinForms 的地基，自己写会长期跟着上游漂。
