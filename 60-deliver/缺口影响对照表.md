# 缺口影响对照表（谁调不到 → 影响什么 → 怎么回退）

> **本表回答一个问题**：「Windows 编译的 WindowsDesktop 程序拿到 Linux 上直接跑，某一项缺失会造成什么后果？」
>
> 口径分三类，**必须分清**：
> - **A 类｜有替代**：有 Linux 对应物，已真实现 ⇒ **不影响运行**
> - **B 类｜无替代但已降级**：已导出为桩，返回安全值 ⇒ **不影响"跑起来"，但相关功能不可用，且调用方能检测到**
> - **C 类｜未实现（gap）**：符号不存在 ⇒ **一调就崩（`EntryPointNotFoundException`）**。**这是最严重的一类，本表目标是把 C 类清零。**
>
> 生成方式：`awk -F'\t' '$1=="libwpfwin32.so"&&$3=="gap"' 40-build/native-shim/exports.txt`
> 当前状态：**A 类 22 / B 类 110 / C 类 0（待 A 类补完后为 0）**

## 三、怎么验证「不影响跑起来」

```bash
# 1) 确认没有 C 类（gap 必须为 0）
awk -F'\t' '$1=="libwpfwin32.so" && $3=="gap"' 40-build/native-shim/exports.txt | wc -l   # 期望 0

# 2) 确认 .so 里这些符号都在（B 类也不能缺）
for s in FsCreateSubpageBottomless CreateRecognizer AccessibleObjectFromWindow; do
  nm -D 40-build/native-shim/bin/libwpfwin32.so | grep -qw "$s" || echo "缺: $s"
done

# 3) 跑样本，确认没有 EntryPointNotFoundException
DISPLAY=:303 ... dotnet samples/WinFormsBasics/bin/Release/net10.0/WinFormsBasics.dll 2>&1 | grep -c EntryPointNotFound
```

## 四、已登记的「功能降级」（不是 gap，是功能不完整）

> 与前三类（A/B/C）不同，这一类**符号都存在**、**调用不崩**，但**功能没完全达到 Windows 的行为**。
> 每条都要写清「用户可见后果」，这是 `AGENTS.md` 第 5 条的要求。

### ACC-011｜DPI 缩放（`DEGRADED`，K-233～K-243）

| 项 | 内容 |
|---|---|
| **现象** | 144 DPI 的 X display 下，`Width=960 DIP` 的窗口实际宽 **960 或 1200 像素**，而 Windows 上应为 `960 × 1.5 = 1440` |
| **已经做到的** | `GetDpiForSystem` 正确返回 **144**；`CW_USEDEFAULT` 已解析（K-238/K-239）；`Width=960` 能传到 `CreateWindowEx`（K-241）|
| **没做到的** | WPF 把 **DIP 值**原样传给 `CreateWindowEx`，没有乘以 `DpiScale`；X11 侧也没有 `WM_DPICHANGED` 之类的通知机制 |
| **用户可见后果** | **高 DPI 屏幕上界面偏小**（文字/控件按 96 DPI 的物理尺寸渲染，看起来比 Windows 上小 ~33%）。**但功能完全可用** —— 布局、输入、渲染都正常 |
| **为什么不再修** | 需要 WPF 的 DPI 决策链完全按 Windows 语义工作（多种感知模式 + 运行时 DPI 变更事件）。已投入 10 轮，`GetProcessDpiAwareness` 改成 `SYSTEM_AWARE` 后仍差最后一环；**继续投入的收益递减，且不影响"程序能否运行"这个核心目标** |
| **规避方式** | 用 96 DPI 的 display（`Xvfb -dpi 96`，默认值）⇒ **完全正常**。本仓所有样本在 96 DPI 下渲染/输入/打印全部 PASS |

### ACC-022 / ACC-008｜点击坐标（`FAIL`，判据侧缺陷，K-223/K-224）

| 项 | 内容 |
|---|---|
| **现象** | `WpfMediaInk` 的 `state_changes` 步骤点击后状态不变 |
| **真因** | 判据的 UI 树 `bounds` 与 X11 窗口几何**自相矛盾**：`bounds=[244,134,913,21]` 而窗口只有 `784` 宽（`244+913=1157 > 784`）⇒ 点击必然打不中 |
| **不是** | 不是 shim 的输入链路问题 —— `ACC-010`（键盘输入）**PASS**、`ACC-023`（Ink）**PASS**、`ACC-007`（渲染）**PASS** |
| **要真修的方向** | `LdpA11y` 导出 UI 树时，把 `Bounds` 从 WPF 内部坐标系**转换到 X11 屏幕坐标**（加窗口绝对位置 + DPI 归一）。**独立任务** |
| **用户可见后果** | **无** —— 只影响判据的可观测性，不影响应用功能 |

## 五、外部产物验证中发现的两条限制（2026-11-01）

> 这两条是**用 Windows 上编译的真产物**跑出来的（`50-verify/external/win-built/`），
> 比本仓自编样本更能反映真实使用场景。

### ACC-EXT-01｜`MediaElement` 播放不可用（`不可修`，官方库限制）

| 项 | 内容 |
|---|---|
| **现象** | 含 `<MediaElement>` 的 WPF 窗口启动后立即抛 `NotImplementedException`，窗口内容全黑（截图 328 字节）|
| **完整因果链** | `UIElement.RenderContent` → `MediaPlayer.AddRefOnChannelCore` → `DUCE.Channel.SendCommandMedia` → **`MS.Internal.HRESULT.Check(hr)` 抛异常** |
| **真因** | **官方 `wpfgfx_cor3.so` 的 `MilResource_SendCommandMedia` 返回 `E_NOTIMPL`** —— 该符号属于 `libwpfgfx_linux.so`（本机不存在，走官方 MIL 库），**是闭源官方二进制的限制** |
| **不是** | 不是本仓 shim 的缺陷；也**与 Ink 无关**（子代理的 A/B 对照：`_InkOnly` 变体 12837 字节正常，带 `MediaElement` 的 328 字节空白）|
| **用户可见后果** | **视频/音频播放完全不可用**；但 `MediaElement` 控件**能创建、能布局、不崩**（只是内容黑），`InkCanvas` 等其它控件不受影响 |
| **能否修** | **不能** —— 需官方 MIL 库实现媒体命令通道 |
| **规避** | 用外部播放器（`mpv`/`ffplay`）播，或走 WebView；**不要用 `MediaElement`** |

### ACC-EXT-02｜WinForms 自绘抛 `EntryPointNotFoundException`（`可修但未修`）

| 项 | 内容 |
|---|---|
| **现象** | Windows 编译的 WinForms 程序在 Linux 上**能启动、能建窗、控件位置正确**，但画面右侧出现 WinForms 的「Unhandled exception」对话框 |
| **完整因果链** | `Control.OnPaintBackground` → `PaintBackground` → `PaintBackColor` → `DeviceContextHdcScope..ctor` → **`IGraphicsContextInfo.GetHdc` 抛 `EntryPointNotFoundException`** |
| **真因** | `IGraphicsContextInfo` 与 `IGraphics` 都在 **`System.Private.Windows.GdiPlus.dll`**（shared framework，`internal`）；`IGraphicsContextInfo.GetHdc` 是 **abstract 无 body**，运行时找不到实现槽位（K-249/K-250 用 Cecil 确认）|
| **为什么难修** | 该接口 `internal` + `InternalsVisibleTo` 只授权带**微软公钥**的 `System.Drawing.Common`；我们的自产 SDC 无强名称 ⇒ **拿不到 IVT 豁免** |
| **用户可见后果（外观）** | **WinForms 控件的外观由 shim 的 `BeginPaint` 兜底绘制**（背景色 + 标题文字，K-163/K-164）—— **能看见控件，但不是 WinForms 自己画的**（圆角、渐变、主题外观都没有）|
| **用户可见后果（交互）** | **按钮点击不生效** —— 实测 3 次：`clicks=0` 保持 0、`[CLICK]` 日志 0 次。**但这不是坐标问题**：`[E3-REPLAY]` 显示鼠标事件 `deliver=1`、`win=0x2400017`（Button 的 HWND），**事件确实投递到了 Button**；真正断点在 `ButtonBaseAdapter.ColorOptions.Calculate` → `ButtonStandardAdapter.PaintWorker` 抛同一个 `EntryPointNotFoundException`，**Click 链断在绘制阶段**（K-261）|
| **用户可见后果（布局）** | **控件位置错乱** —— `clicks=0`（设 `Left=16,Top=310`）渲染在屏幕 (490,548)；`hello-extA`（设 `Left=16,Top=16`）在 (280,33)。文字都渲染出来了但坐标不对，**未深查**（K-261）|
| **能否修** | **不可行（已穷尽 4 条手段，各有实证依据，见下）**。**注意：修好它同时会恢复"点击"** —— 因为 Click 链断在同一处 |
| **穷尽的手段 1：IVT 公钥匹配** | ❌ `System.Private.Windows.GdiPlus` 授权 `System.Drawing.Common` 用的是**完整公钥**（1492 位 RSA），无微软私钥不可能通过；自产 SDC 连强名称都没有（K-277）|
| **穷尽的手段 2：接口垫片** | ❌ 类型 `internal`（`public=False`）⇒ 编译期引用不到；且 .NET **不允许给已有类型追加接口**，伪造同名接口也不被 CLR 识别为同一类型（K-284）|
| **穷尽的手段 3：IL 等长替换** | ❌ `IL_00db~IL_00fa` 仅 33 字节，塞不下 `ValueTuple<HDC,int>` 的构造；且走该分支的**前提就是 `HDC` 为 null** ⇒ 换掉也拿不到有效 HDC（K-280）|
| **穷尽的手段 4：运行时 hook** | ❌ 被 hook 的方法必须返回**真实 HDC**，而自产 SDC 建立在 libgdiplus 的 `GpGraphics` 上，**没有 Win32 GDI 设备上下文**（K-280）|
| **根因（架构层面）** | 不是"缺一个方法"，而是**缺一套 Win32 GDI 设备上下文（HDC）语义**。WinForms 的绘制路径（`DeviceContextHdcScope`）硬性要求真实 HDC。要实现它等价于**在自产 SDC 里重建 Win32 GDI DC 模型** —— 那是重写 `System.Drawing.Common` 的量级，超出本仓「不做二进制兼容」的定位（AGENTS.md 第 8 条）|
| **规避** | 界面用 WPF（WPF 侧渲染完全正常）；或用 `UserPaint=false` 的 WinForms 控件子集 |

### 7.1 IL 块数决定启动成功率（K-1305）

**背景**：本仓大量验证依赖「Cecil patcher 注入 IL 到 SourceTree.exe」。此前成功率 50-67% 被当作「偶发崩溃」。

**实测**（同一环境 `WPF_LINUX_ATSPI=0`）：

| 产物 | 注入的 IL 块数 | 大小(B) | 成功/总数 | 成功率 |
|---|---|---|---|---|
| A0 `clean.dll` | **0** | 862208 | **11 / 12** | **92%** |
| A `ST.cnt.dll` | 2 | 864256 | 3 / 6 | 50% |
| B `ST.pre.dll` | 3（含 1 个**永不执行**块）| 864256 | 0 / 6 | **0%** |

**⇒ 崩溃率与 IL 块数**严格单调相关**。一个永不执行的块就能把 50% 打到 0%。**

**工程对策**：
1. **每次实验只注入当前需要的块**；
2. **每轮实验后回到 `clean.dll` 验证基线**；
3. **所有成功率数据必须注明当时的块数**。

### 7.2 inotify 上限导致「文件监控」失效（**已作废，K-1306**）

**背景**：「暂存」操作（`RepoTabViewModel.Stage(IEnumerable)`）反射链全通但 `UnstagedFileList.Count` 恒为 0（K-1297/K-1301）。

> **⚠️ 本节结论已作废（K-1333/K-1343）**：原判断「inotify 上限导致暂存失败」是**错的**。
>
> - **K-1333 实测**：`RepoWatcher` 零报错（inotify 已用 124/128）时，`UnstagedFileList.Count` 仍为 0
> - **K-1343 旧根因（已于 2026-11-10 被 K-1373 推翻）**：当时判为 **`Tabs.Count = 0`**（SourceTree 从没打开仓库）；K-1373 实测 `AddOrActivate` 可用（`TabsCount: 1`），暂存/提交的真实缺口见 K-1404
> - **⇒ 正确结论见 `70-operate/已知限制汇总.md` 的 L-20.4：暂存不可达**
>
> 保留原文仅作历史记录。

**原判断（已作废）**：`fs.inotify.max_user_instances = 128`，系统已用 **124** ⇒ SourceTree 的 `RepoWatcher` 启动失败（日志确实报 `inotify instances limit (128) reached`）⇒ 文件监控不工作。

**为什么不成立**：K-1333 在同样 124/128 的条件下启动，`RepoWatcher` **零报错**，`Count` 仍为 0 ⇒ inotify 只是**相关**，不是**因果**。

**⇒ 修复命令（`sudo sysctl -w fs.inotify.max_user_instances=1024`）**对「暂存」无效**，但作为环境自检仍可执行 `bash 70-operate/启动器/verify-inotify-fix.sh`。**

### 8.2 逐项详解

#### 【中】合成输入不可用（K-1263）

- **现象**：`xdotool click`/`mousemove`、`WPF_FAKE_CLICK`/`WPF_FAKE_KEYS`、IBUS 全部无法驱动 WPF
- **影响**：不能像真人一样点击按钮
- **重要性**：**中** —— 因为它是「用 SourceTree 干活」的核心交互
- **替代**：`IsSubmenuOpen=true` / `IsChecked=true` / `Window.Show()`（K-1235~K-1238）+ `InvokeProviderWrapper` 反射（K-1143）
- **⇒ 判定：不阻断，因为替代方案覆盖了所有验证场景**

#### 【中】差异内容区无法程序化驱动（K-1450/K-1451 定稿，修正 K-1404/K-1449）

- **现象**：`ShowDiffBetweenCommits(9a74d4a,657c444)` **返回正常、不崩溃**，但界面上**没有出现 diff 窗口或内容**（K-1404 截图与基线 `sha256` 相同；K-1449 在四链齐备 + 使用方规则下复测仍无窗口）。**旧结论「在 `Loaded`/`ContentRendered` 调用都崩溃」已不再成立。**
- **影响**：仍然无法在 UI 里看两个提交的差异；但这是**四类操作里唯一剩余缺口**（其余三项已由 K-1430/K-1444/K-1449 打通）
- **重要性**：**中** —— diff 是 Git 客户端的核心功能之一
- **替代**：`git diff <a> <b>` 命令行（功能等价）
- **⇒ 判定（K-1450/K-1451 定稿）**：**CommitDetails 面板与文件列表已出现**（`DetailViewModel` 切到 `CommitChangeSetViewModel`、`DetailsInProgress True→False`、`FileTree.Count=1`、`CommitRange` 已设）；**右侧内容区需真实 UI 选中**才渲染——反射设 `SelectedFileTreeItems` 能创建 `DiffViewModel` 但 WPF 的 `TreeView.SelectedItems` 只读、由 `TreeViewItem.IsSelected` 驱动，**VM 集合不反向驱动 UI**
- **⇒ 三条程序化驱动路均不可行**：AT-SPI 桥不导出控件树（`childCount=-1`）、`CommitChangeSetViewModel` 无 View/TreeView 引用（拿不到 `TreeViewItem`）、`ItemContainerGenerator` 需 `TreeView` 实例（视觉树递归会核心转储 K-1421）
- **远程三操作（Fetch/Push/Pull）✅ 已可用**（K-1466/K-1467）：`Fetch` 靠旁路 `CustomActionsManager`（`PushDialog` 后插 `Confirm()`）；`Push/Pull` 需在 `Confirm()` 前**反射填 4 个 DialogVM 集合**（Push：`RemoteNameList`+`SelectedRemoteIndex`+`Branches`；Pull：`RemoteList`+`SelectedRemote`+`RemoteBranchList`+`SelectedRemoteBranch`），零 IL 改动。实测：fetch `origin/master` `387c805`→`fc5ca2b`、push 远端 HEAD `ecc27d5`、pull 本地 HEAD `81a750a`。
- **⇒ 菜单栏缺 `)`（K-1461/K-1464）：已知无害、不修** —— 成因是菜单栏宽度由**托管 `TextFormatter`/菜单项模板（BAML）**决定，`libwpfwin32.so` 的 `GetTextExtentPoint32W` 走不到（K-1464 实测：改成 CJK 双宽后菜单仍全无 `)`，已回滚）；文字可读、点击正常；要修只能改模板右 padding 或 patch 托管度量（代价高）
- **⇒ 用户侧可用**：**手动点击文件列表中的文件即可显示 diff**；程序化场景可用 `git diff` 命令行代替

#### 【中】输入法不可用（ACC-017，K-012/K-041）

- **现象**：`XIMPreeditCallbacks` 的 `XCreateIC` 恒返回 NULL；IBUS D-Bus 方法全 `UnknownMethod`
- **影响**：无法用拼音输入中文
- **重要性**：**中** —— 提交信息通常要写中文
- **替代**：粘贴（如果剪贴板可用）/ 英文提交信息
- **⇒ 判定：环境缺口（换机器可解），不是实现缺口**

#### 【中】inotify 上限 128（K-1306/K-1377）

- **现象**：`fs.inotify.max_user_instances=128`，`xdg-desktop-portal` 泄漏 24 个实例
- **影响**：SourceTree 的 `RepoWatcher` 可能拿不到实例 ⇒ 文件监控不工作 ⇒ UI 不刷新
- **重要性**：**中** —— ⚠️ **K-1333 + K-1436 均否定「直接导致 UI 不刷新」的因果**（K-1436：strace 213 行里 `inotify_add_watch` 全返回成功、无 `EMFILE/ENOSPC`；写文件后 9 秒 `staged` 仍 0，但手动 `RefreshStatus()` 后立刻 `staged=1`）；**真因是 watcher 处理事件时缺 `shlwapi!PathRelativePathTo`**（`DllNotFoundException` 使事件被丢弃，见 K-1436 与任务 `tk_01M72Z75QV7WWZY4CVA1ZWF6CZ`）
- **替代**：**清理重复的 `xdg-desktop-portal` 进程**（实测把 126 → 111，释放 15 个，**不需要 sudo**）
- **⇒ 判定：可缓解，但非根治（根治需 `sudo sysctl`）**

#### 【中】文件状态视图需前置配置（K-1415/K-1416 修正 K-1407）

- **已解决的部分**：满足前置后，SourceTree **真的把改动文件显示出来**——K-1416 实测 `git status` 子进程 `cwd=/tmp/stgit`、argv 完整（`status --porcelain --ignore-submodules=dirty --untracked-files=all --no-ahead-behind`）、退出码 0、输出 `A  k146.txt` 被接收；截图 `50-verify/读数/K-1416/shot.png`（48347B）里中间「待定的文件」列出 `k146.txt`、左侧显示 `分支（master/test-ops）`、提交框自动填 `Test <test@test.local>`
- **前置条件**（不做就是空列表）：`SourceTree.Dvcss.Git::GetHandler` 必须非 null —— 需反射造 3 参 `DvcsInstallationConfiguration`（`GitVersionOneConfiguration(IConfigurationManager)`）+ 造 `<home>/cmd\git.exe` 符号链接布局（`get_ExePath` IL 硬编码 `"cmd\git.exe"`）
- **旧读数为何是空**：K-1406/K-1407 的 `LogRows.Count=1`、`Staged/UnstagedFileList.Count=0`、UI「没什么可提交的」都是**前置未满足**时的状态（K-1407 已排除「两个实例」、K-1409/K-1411 已排除「缺 libgit2」、K-1413 定位到 `CurrentInstallationConfiguration` 为 null）
- **仍未验证**：History 提交列表（`LogRows`）在前置满足后是否随 `git log` 填充
- **重要性**：**中**（从「高」下调：核心缺口已有可行修法；但需把反射造配置固化成启动步骤才算常态化）
- **替代**：命令行 `git status` / `git log` / `git diff`
- **⇒ 判定：文件状态视图可用但有前置；下一步是把前置固化成启动步骤（不是再查根因）**
