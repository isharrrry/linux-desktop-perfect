**D-011 第 19 步（2026-10-31）—— 缩小到 WPF 的 `TranslateAndDispatchMessage` 判定层**：
读上游 `WindowsBase/.../Dispatcher.cs`：
```csharp

                    UnsafeNativeMethods.DispatchMessage(ref msg); }
}
```
⇒ **`DispatchMessage` 只在 `handled == false` 时被调**。而我们的读数说
`DispatchMessageW` 收到 23 条别的消息、**唯独没有 0x0233** ⇒ 那一条的 `handled` 是 `true`。
再读 `ComponentDispatcherThread.RaiseThreadMessage`：

```csharp
if (handled) return handled;
if (_threadPreprocessMessage != null) _threadPreprocessMessage(ref msg, ref handled);

```
⇒ `handled` 只能是**订阅者**置的。但 `grep ThreadFilterMessage/ThreadPreprocessMessage`
在 `PresentationFramework/` 下**没有任何结果** ⇒ **看起来没人订阅** ⇒ `handled` 应为 false。
**⇒ 这里有个未解的矛盾**：要么订阅者在 `PresentationCore`/`WindowsBase` 里（我 grep 的范围只到

**下一步（三条并列，按成本排序）**：
1. 在 shim 的 `TranslateMessage` 里打 `msg->message`（看它是否被改）；

⇒ **DC 通过、AC 失败**：bit 流起点是对的、DC 霍夫曼表也是对的，问题在 **AC 霍夫曼解码**（可能是 `jpeg_huff_build` 的 mincode/maxcode 计算，或 AC 表里 EOB 码字的位置）。**第四步（2026-10-30）—— 找到真正的 bug：`jpeg_huff_build` 漏了 `valptr` 的累加**。把 AC 表打出来后发现 `valptr` **全是 0**（每个码长的起点都没推进）⇒ 所有码字都从 `vals[0]` 起算 ⇒ AC 解出的符号张冠李戴（全黑图的 EOB 被解成非零系数，一路读到 k>=64 才失败）。修法是循环里补一句 `k += bits[len-1]`。
