**第七步（2026-10-30，走路线①）**：加了补丁 **P20**（`apply.mjs` 的定点补丁）—— 在 `HwndSource.HwndTargetFilterMessage` 里处理 `WM_DROPFILES`：`WpfLinuxDroppedFiles`（自带 `DragQueryFileW/DragFinish` 的 `DllImport`）读 HDROP → 构造 `DataObject(FileDrop)` → `DragEventArgs` + `DragDrop.DropEvent` → `RootVisual.RaiseEvent`。PresentationCore 编译通过（含补丁）、全链重建、样本重建。**第八步（2026-10-30，诊断证否）**：在 P20 里加了一行诊断 `[P20] WM_DROPFILES wParam=…` 后重跑 —— **诊断 0 次** ⇒ `WM_DROPFILES` **根本没到** `HwndTargetFilterMessage`。同时确认了一个容易搞错的点：shim 里 `HWND == X11 Window`（`wpf_window.hwnd` 的注释写明），所以`push(t, (HWND)ev.xselection.requestor, WM_DROPFILES, …)` 的窗口标识**是对的**。⇒ 问题在 **`push` 的队列/线程路由**或消息循环的取用上（`push` 有"按窗口 owner_thread 路由"的 F8 机制），不在补丁、也不在窗口标识。

**第九步（2026-10-30，路由证正）**：在 `push()` 里对 `WM_DROPFILES` 加诊断后实测：`[XDND-PUSH] WM_DROPFILES hwnd=0x200005 wp=0x… pump_thread=0x… owner=0x… -> target=0x…` —— **消息进了正确的线程队列**（`target == owner_thread == pump_thread`）。所以 `push` 的路由没有问题；剩下的是 **`GetMessage/PeekMessage` 侧的取出/过滤**：WPF 的 `HwndTargetFilterMessage` 根本没被调到，说明这条消息在 `win32_msg.c` 的取消息路径上被跳过或没被派发。下一步查 `GetMessageW/PeekMessageW` 的过滤条件（`hwnd` 范围、`lo/hi` 区间、或内部丢弃表）。

**第十步（2026-10-30，过滤条件已排除）**：读了 `wpf_queue_pop` 的过滤逻辑，只有两条：①`hwndFilter && m->hwnd != hwndFilter && m->message != WM_QUIT`；②`lo || hi` 的消息区间。WPF 的 `GetMessage` 传 `hwnd = NULL`、区间 0 ⇒ **两条都不成立**，`WM_DROPFILES` 应能正常取出。⇒ 过滤不在 shim 的队列里，问题在 **WPF 取到消息之后的分发**（`HwndSource` 只在"自己知道的 hwnd"上派发，或 `HwndTargetFilterMessage` 不在那条消息的 hook 链上）。
**第十一步（2026-10-30，定位到"入了队但没被取走"）**：读代码找到 WPF 的消息总入口是 `Shared/MS/Win32/HwndWrapper.WndProc`（hook 链在它里面遍历），加了补丁 **P21**：在 WndProc 入口对 `WM_DROPFILES` 打诊断。实测：
```
[XDND-PUSH] WM_DROPFILES hwnd=0xa00005 wp=0x… pump_thread=0x… owner=0x… -> target=0x…
（P21 / P20 诊断均 0 次）
```
⇒ **消息确实入了对的线程队列，但 WPF 从未在 `WndProc` 里见到它** ——— 即 `GetMessage`/`DispatchMessage` 这一段没有把它取出来派发。下一步读 `win32_msg.c` 的 `GetMessageW`：看它是否"先 pump X 再取队列"、或取消息时带了别的隐式条件（例如只在 `hwnd` 已知时取、或 pump 之后直接返回不 re-check 队列）。
