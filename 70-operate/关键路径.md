# 关键路径与接管

> 本文档记录「只有单一维护者能改」的路径，目的是让第二个维护者能在不重建全部上下文的情况下接手。
> **它不改变任何评分**：`bus_factor` 由 git 近 90 天作者数决定，写文档不会提高该读数（评估口径见 [#评估轮次索引](../50-verify/audit/README.md)）。
> 每条坑都指向 [《已知坑与降级清单》](已知坑清单.md) 的真实编号；编号只在定义方定义，本文只引用。

八子系统与模块编号的唯一定义方是 [《概要设计》](../30-design/概要设计.md) §4；验收编号的唯一定义方是 [《需求与验收判据文档》](../20-spec/需求与验收判据文档.md)。

## SYS-1 wpf-port

**入口**：`40-build/wpf-port/build-port.mjs`（自产托管件构建）、`40-build/appliers/apply.mjs`（派生树生成）、`40-build/appliers/apply-bin.mjs`（二进制补丁）。

**最小验证命令**：

```bash
node 40-build/appliers/apply.mjs --check
```

判读：输出 `问题 0` 即通过；`计划改写 N 个文件` 是待应用提示，不等于失败（实测 rc=0，`1 个待改写`）。

**常见坑**：

- `K-1457` —— 确认框补丁必须走 applier（`40-build/appliers/commit-noconfirm/`），手改 DLL 会被下次生成覆盖。
- `K-1434` —— 三处 DLL 补丁的顺序被强制为 `brush→minreq→seticon`，顺序错了产物哈希就不同。
- `K-1305` —— 注入 IL 的块数与崩溃率严格单调相关（0 块 92% → 2 块 50% → 3 块 0%），加补丁前先数块。

**接管步骤**：

1. 读 `40-build/appliers/build-flags.json`，确认补丁清单与顺序。
2. 只改 `40-build/appliers/<补丁名>/`，不改派生树 `40-build/build/wpf/`（那是产物）。
3. 重生成派生树并跑 `--check`，确认「问题 0」。
4. 跑 `node 40-build/pack/build-pack.mjs --check`，确认自产替换件数未掉。

## SYS-2 native-shim

**入口**：`40-build/native-shim/build-shim.sh`、`40-build/native-shim/src/`（`win32_*.c`）、`40-build/native-shim/exports.txt`（导出契约）、`40-build/native-shim/src/win32_abi.h`（ABI 断言）。

**最小验证命令**：

```bash
cc -fsyntax-only -I40-build/native-shim/src 40-build/native-shim/tests/abi_layout.c
```

判读：`rc=0` 无输出即通过。全量重建用 `make -C 40-build/native-shim`（本机 `make` 可用）。

**常见坑**：

- `K-1464` —— 菜单栏缺 `)` 不能靠 `GetTextExtentPoint32W` 双宽修复，WPF `Menu` 走托管文本路径。
- `K-1379` —— 缺 `WPF_LINUX_ATSPI=0` 会白屏，启动脚本必须在环境里带上。
- `K-1446` —— 四链（A/B/C/D）验收可回退可复现，改 shim 后按四链哈希逐项对。

**接管步骤**：

1. 改 `src/*.c` 后先 `make -C 40-build/native-shim`，再 `nm -D bin/libwpfwin32.so` 与 `exports.txt` 对导出。
2. 新增导出必须同时补 `win32_abi.h` 的字段断言（`abi_layout.c` 是判据，不是注释）。
3. 跑 `node 50-verify/deliver-check.mjs`（L1 静态）确认四链与能力可达性。
4. 需要动态验收时再看 `--with-gui`（依赖 Xvfb 与本机运行时，见该脚本头部）。

## SYS-3 milcore

**入口**：`40-build/milcore/WpfGfx.Linux.csproj`（DUCE 解码与 Skia 后端）、`40-build/milcore-bridge/build-bridge.mjs`（AOT 导出层，产出 `wpfgfx_cor3.so`）。

**最小验证命令**：

```bash
node 40-build/milcore-bridge/build-bridge.mjs --check
```

判读：输出 `产物就绪` + `rc=0` 即通过（实测通过）。

**常见坑**：

- `K-005` —— 仓里有三份 WpfGfx 源码，媒体/bridge 改动曾长期改在错误的文件上；动手前先确认改的是 `40-build/milcore/`。
- `K-1392` —— 字体引擎实际在 `wpfgfx_cor3.so` 里（`MilFontFace_RegisterFromFile`），不在 text-stack。
- `K-1308` —— `RenderTargetBitmap` 构造成功但 `.Render()` 失败，别把「构造成功」当渲染可用。

**接管步骤**：

1. 先在 `40-build/milcore/` 内定位命令实现（`Commands/`、`Rendering/`、`Resources/`）。
2. 改后构建 bridge 并 `--install <dotnetRoot>` 装入框架根，否则运行时仍加载旧件。
3. 跑 `node 50-verify/deliver-check.mjs` 与对应 ACC 判据。

## SYS-4 text-stack

**入口**：`40-build/text-stack/Makefile`、`40-build/text-stack/src/dwlinux.c`、`40-build/text-stack/src/dwlinux.h`（**唯一声明处**）。

**最小验证命令**：

```bash
cc -fsyntax-only -I40-build/text-stack/src 40-build/text-stack/tests/text_abi.c
```

判读：`rc=0` 无输出即通过（实测通过）。该文件用 `_Static_assert` 钉死窗口结构，改了结构会在这里报错。

**常见坑**：

- `K-1392` —— 字体枚举与回退链的真实现所在位置容易找错，先看该条再改。
- `K-1399` —— 7 种字体请求里 4 种仍失败，改字体前先确认失败的是「解析」还是「渲染」。

**接管步骤**：

1. 改 `dwlinux.h` 即改跨语言 ABI，必须同步 `tests/text_abi.c` 的断言。
2. `make -C 40-build/text-stack` 后跑 [《需求与验收判据文档》](../20-spec/需求与验收判据文档.md) 的 ACC-013/ACC-014/ACC-015。
3. 双路径对拍依赖 `50-verify/text/hb-oracle.py`（不共享代码的参考实现），改完重跑对拍。

## SYS-5 wic-dwrite

**入口**：`40-build/wic-dwrite/Makefile`、`src/png_decode.c`/`jpeg_decode.c`/`mscms.c`、`tools/wic-dec-probe.c`（探针）。

**最小验证命令**：

```bash
make -C 40-build/wic-dwrite symbols
```

判读：列出 `libwpfwic.so` 的导出符号；构建用 `make -C 40-build/wic-dwrite`（产出 `bin/libwpfwic.so`）。

**常见坑**：

- `K-1390` —— PNG 解码本身正常（RGBA 可解），不支持调色板 PNG（color type 3），别把图标缺失归到解码器。
- `K-1396` —— 图标问题是「没进渲染树」，不是 WIC/COM 代理不支持；先查渲染树再改 WIC。

**接管步骤**：

1. 先跑 `wic-dec-probe` 分辨是「解码失败」还是「渲染树没拿到」。
2. 改 `src/*.c` 后 `make -C 40-build/wic-dwrite`，再跑 `tools/wic-dec-probe` 看头解析与像素。
3. 跑 ACC-018/ACC-019 判据；新增格式必须同时补探针与判据，不许只加解码器。

## SYS-6 pack

**入口**：`40-build/pack/build-pack.mjs`、`40-build/pack/FrameworkList.xml`（件清单）、`40-build/pack/install-runtime.mjs`（安装）、`40-build/sdk/LinuxDesktopPerfect.WindowsDesktop.targets`（`UseWPF` 解析）。

**最小验证命令**：

```bash
node 40-build/pack/build-pack.mjs --check
```

判读：`rc=0` 即通过；输出里的 `原生件待补 libwpfgfx_linux.so（LDP-E-PACK-207）` 是**已知降级读数**，不是本次失败。

**常见坑**：

- `K-1405` —— 共享框架「现装件」不是单一产物（基线 + 手工替换 + 别名副本），不要以安装清单计数推断一致性。
- `K-1403` —— 单件重编译确定性可复现（三次同哈希）；out/pack 与今天产物的差异来自派生树重生成，不是编译不确定。

**接管步骤**：

1. 增删件先改 `FrameworkList.xml`，再让 `build-pack.mjs` 生成，不手改 `out/`。
2. 跑 `node 40-build/pack/install-runtime.mjs --check` 确认用户目录框架与 pack 一致。
3. 跑 ACC-001~ACC-004；身份（公钥 token）不对会直接失败，见 `D-003`。

## SYS-7 winforms-compat

**入口**：`40-build/winforms-compat/`（当前只有 `.gitkeep`，**尚未实现**）；已落地的兼容面在 `40-build/native-shim/src/win32_winforms_extra.c`。

**最小验证命令**：

```bash
ls 40-build/winforms-compat
```

判读：当前只有 `.gitkeep` 即为「未实现」的预期状态；没有可判定的功能验证。

**常见坑**：

- `D-016` —— WinForms 兼容层未自产：样本启动即 `DllNotFoundException: KERNEL32.dll`，且上游 `40-build/upstream/` 只有 wpf 源码，需先拉 winforms。
- `K-1359` —— 四类操作（提交查看/差异/提交/切分支）的当前状态表在交付清单里，不要凭记忆判断。

**接管步骤**：

1. 先确认能否取到上游 winforms 源码（网络受限，见 `D-016`）。
2. 取到后再决定「自产兼容层」还是「补 shim 的 kernel32 面」，两者工作量差一个量级。
3. 任何推进都必须先在 `50-verify/winforms/` 落一条红判据（AGENTS 第 9 条）。

## SYS-8 service-adapters

**入口**：**分散，无单一大门**——媒体在 `40-build/media-bridge/`，UIA/AT-SPI 在 `40-build/native-shim/src/win32_atspi.c`，打印在 `40-build/wpf-port` 的 ReachFramework 件，Ink 在 `40-build/milcore-bridge` 与样本侧；`40-build/service-adapters/` 目前是空目录。

**最小验证命令**：

```bash
make -C 40-build/media-bridge
```

判读：产出 `bin/libldpmedia.so` 即编译通过；播放行为另由 ACC-022 判定。

**常见坑**：

- `K-005` —— 媒体改动曾长期改在错误的 WpfGfx 源码上，动手前先确认文件。
- `K-1438` —— 合成输入（`WPF_FAKE_CLICK`/`WPF_FAKE_KEYS`）投递层有效、UI 反应不可依赖，别把「投递成功」当功能可用。
- `K-1464` 与 `K-1446` —— 界面类改动最终以四链与 AT-SPI 结构树为准，不以截图为准。

**接管步骤**：

1. 按 MOD 号定位：MOD-81 UIA / MOD-82 打印 / MOD-83 媒体 / MOD-84 Ink / MOD-85 DRM。
2. 逐个跑对应 ACC（ACC-022 媒体、ACC-023 Ink、ACC-024 打印、ACC-027 UIA）。
3. 新增能力必须同时登记降级项（[《已知坑与降级清单》](已知坑清单.md) 的 `D-*` 行，5 列格式）。
