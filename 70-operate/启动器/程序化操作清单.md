# 程序化操作 SourceTree 的 6 条使用方规则

> 用反射/IL 注入方式驱动 SourceTree（不开鼠标、不点按钮）时，下面 6 条是**必须满足的前置**。
> 每条都附「代码片段 + 验证判据 + 不满足时的现象」。顺序不能乱：**① → ② → ③ → ④ → ⑤ → ⑥**（⑥ 只在需要远程操作时用）。
>
> 参考实现：[Helper.cs](profiles/Helper.cs)。坑的完整证据见[《已知坑与降级清单》](../../70-operate/已知坑清单.md)对应 K 号。

## 规则总览

| 顺序 | 规则 | K 号 | 不满足时 |
|---|---|---|---|
| ① | 反射注入 Dvcss 安装配置 + 造 `<home>/cmd\git.exe` 布局 | K-1413 / K-1415 | `GetHandler` 为 null ⇒ 任何 VCS 操作都不执行，列表恒空 |
| ② | `AddOrActivate(path, mode, null)` 打开仓库 | K-1373 | 无 tab、无视图 |
| ③ | **补调 `RepositoryMonitorManager.ActivatedTab(path)`** 启用文件监控 | K-1445 | 写文件后列表不自动刷新（`staged` 恒 0） |
| ④ | `AddOrActivate` 后**等至少 1 个 tick（3 s）**再调 `NavigateToView(Log, null)`/设 `CurrentRepoView=1`；**立刻调会被窗口初始化覆盖**（K-1453） | K-1421 / K-1453 | `AddOrActivate(..., Log, ...)` 后 UI 仍停在「文件状态」；或设值后 tick1 立刻回到 `FileStatus` |
| ⑤ | **切到 `Log` 视图后 History 会自动加载**（无需调任何 API；K-1448 三组对照：`tick1~4` 均 `logRows=1`，切视图后 3 秒内直接变 **34**，且**不依赖 `ActivatedTab`**）。`LoadNextLogBatchFrom(0,(uint)500)` 仅用于**加载更多**（显式调一次与自动结果同为 34，无额外贡献）；若要调必须带 `NonPublic` flags、第二参数 `UInt32`，读数放 `DispatcherTimer` 里 | K-1419 / K-1420 / K-1447 / **K-1448** | History 列表空；**`GetMethod` 不带 NonPublic ⇒ 返回 null ⇒ 反射调用抛 `NullReferenceException`（假故障，K-1447）；传 `500`（int）⇒ `ArgumentException`**；`Thread.Sleep` 会阻塞回填、后台线程读会核心转储 |
| ⑥ | **远程操作（fetch/push/pull）**：fetch 需先旁路 `CustomActionsManager` 对话框（IL 补丁，仅探针用）；push/pull 需在 `Confirm()` 前反射填 DialogVM 集合（字段见下） | **K-1466 / K-1467** | fetch 卡在「自定义动作」对话框不返回；push/pull 抛 `NullReferenceException`/`ArgumentException`（集合为空）或什么都不发生 |

## ① Dvcss 配置注入 + `cmd\git.exe` 布局（K-1413 / K-1415）

**为什么**：`SourceTree.Dvcss.Git::GetHandler` 第一步读 `CurrentInstallationConfiguration`，为 `null` 就直接 `ret null`（K-1413）；该字段只在「安装/切换版本」的 UI 路径才被写，启动路径不写。

```csharp
var vm   = (object)window.DataContext;                       // MainWindowViewModel
var dvcs = Prop(vm, "DvcssManager").GetType().GetMethod("GetDvcs").Invoke(Prop(vm, "DvcssManager"),
             new object[] { 0 /* RepoType.Git */ });
var cfgMgr = Prop(vm, "ConfigurationManager");               // IConfigurationManager
var verCfg = Activator.CreateInstance(
    Type.GetType("SourceTree.Dvcss.GitVersionOneConfiguration, SourceTree.Dvcs.Git"),   // ctor 是 public
    new object[] { cfgMgr });
// 3 参 ctor：homePath / actualVersion / IDvcsVersionConfiguration（2 参或 1 参会因 VersionConfiguration 为 null 抛 NRE）
var instCfg = Activator.CreateInstance(
    Type.GetType("SourceTree.Model.Dvcss.DvcsInstallationConfiguration, SourceTree.Api.Dvcs"),
    new object[] { Environment.GetEnvironmentVariable("GV_HOME") ?? "/usr", "2.30.0", verCfg });
Field(dvcs.GetType(), "<CurrentInstallationConfiguration>k__BackingField").SetValue(dvcs, instCfg);
```

**布局**：`get_ExePath` 的 IL 硬编码 `"cmd\git.exe"`（反斜杠是字面量，Linux 上会变成一个含 `\` 的**文件名**）⇒ 必须存在 `<GV_HOME>/cmd\git.exe`。用[#dvcss-prereq.mjs](../../40-build/appliers/dvcss-prereq.mjs) 一条命令造出（D 链，见[《交付说明》](../../60-deliver/README.md)）。

**判据**：`dvcs.GetType().GetMethod("GetHandler").Invoke(dvcs, null) != null` 打印 1。

## ② + ③ 打开仓库 **并启用监控**（K-1373 / K-1445）

```csharp
var rtc = Prop(vm, "RepositoryTabContainer");                 // RepositoryTabContainerViewModel
var add = rtc.GetType().GetMethod("AddOrActivate");           // 返回 void，不能 pop（K-1373）
add.Invoke(rtc, new object[] { repoPath, Enum.ToObject(add.GetParameters()[1].ParameterType, 0), null });

// ⚠️ 必须补这三步：AddOrActivate 不注册 watcher（K-1445）
var mm = Field(vm.GetType(), "<RepositoryMonitorManager>k__BackingField")?.GetValue(vm)
      ?? Prop(vm, "RepositoryMonitorManager");
mm.GetType().GetMethod("ActivatedTab").Invoke(mm, new object[] { repoPath });
mm.GetType().GetMethod("RefreshFileSystemMonitoring").Invoke(mm, null);
mm.GetType().GetMethod("SetFileWatcherStatus").Invoke(mm, new object[] { repoPath, true });
Prop(mm, "RepoMonitor")?.GetType().GetMethod("Resume")?.Invoke(Prop(mm, "RepoMonitor"), null);
```

**判据**：进入 timer 后往仓库写文件并 `git add`，**3 秒内** `StagedFileList.Count` 由 0 变 1，且 `git status` 调用次数随之增加（K-1445：补调后 3/3，未补调 1/2~3/5 波动）。

**不满足的现象**：`staged` 恒 0，手动 `RefreshStatus()` 才变 1（K-1440/K-1442）。

## ④ 切视图（K-1421）

```csharp
var tab = Prop(rtc, "SelectedRepoTabViewModel");
tab.GetType().GetMethod("NavigateToView").Invoke(tab, new object[] {
    Enum.ToObject(<RepoViewMode 类型>, 1 /* Log */), null });
// 或：tab.GetType().GetMethod("set_CurrentRepoView").Invoke(tab, new object[] { Enum.ToObject(..., 1) });
```

**判据**：`CurrentRepoView` 读出为 `Log(1)`（且 **tick2 起保持**），`LogVM.LogRows` 在 3 秒内从 1 涨到 ≥17（切到 Log 后自动加载，K-1448）；UI 侧用截图确认左侧 `History` 高亮 + 右侧提交列表（K-1453 的 `shot-history.png` 即是）。
**关键时机**：`NavigateToView`/`set_CurrentRepoView` **必须在窗口初始化完成后调**（`AddOrActivate` 之后至少 1 个 tick）；立刻调会被初始化/保存状态覆盖回 `FileStatus`（K-1453）。
**另一坑**：`AddOrActivate` 会**恢复该仓库上次保存的视图状态**（K-1453）——若上次是 `Log`，本次 tick1 就是 `Log`，别误判成「方法生效」。

**不满足的现象**：`AddOrActivate(path, Log, null)` 之后 `CurrentRepoView` 仍是 `FileStatus`（K-1421）。

## ⑤ 拉 History 数据（K-1419 / K-1420）

```csharp
// 必须在 ④ 之后调用；async void，自身会切回 UI 线程做回填
var logVm = Prop(tab, "LogVM");
// ⚠️ K-1447：该方法是非 public（`Void LoadNextLogBatchFrom(Int32, UInt32)`），
//    不带 NonPublic flags 会拿到 null ⇒ Invoke 抛 NullReferenceException（假故障）；
//    第二参数必须是 uint，传 int 500 会抛 ArgumentException。
const BindingFlags NF = BindingFlags.Instance | BindingFlags.NonPublic | BindingFlags.Public | BindingFlags.FlattenHierarchy;
var ln = logVm.GetType().GetMethod("LoadNextLogBatchFrom", NF);
if (ln == null) throw new MissingMethodException(
    "LogViewModel.LoadNextLogBatchFrom not found — 检查 NonPublic flags（K-1447）");
ln.Invoke(logVm, new object[] { 0, (uint)500 });

// 读取必须放在 DispatcherTimer 的回调里（UI 线程），且不要 Thread.Sleep
new DispatcherTimer(TimeSpan.FromSeconds(3), DispatcherPriority.Background,
    (s, e) => Log("[tick] LogRows=" + Prop(logVm, "LogRows")?.GetType()
        .GetProperty("Count")?.GetValue(Prop(logVm, "LogRows"))), window.Dispatcher);
```

**判据**：`LogRows.Count` 从 1（`AddLoadingRow` 的占位行，K-1418）变 ≥2（有 16 个历史提交时实测 17~19），且截图里 History 面板列出提交行。

**不满足的现象**：`LogRows.Count` 恒 1；若用 `Thread.Sleep` 等则回填 continuation 被阻塞；若从后台线程读 `ObservableCollection` 则核心转储（K-1419）。

## ⑥ 远程操作：fetch / push / pull（K-1466 / K-1467）

三条命令的共同点：**SourceTree 会先弹一个对话框**，`Confirm()` 之后才真正执行 git。程序化路径下要么旁路对话框（fetch），要么在 `Confirm()` 前把 DialogVM 的集合填好（push/pull）。

### ⑥-1 fetch：旁路 `CustomActionsManager`（需 IL 补丁）

`RepoTabViewModel::Fetch` 里调完 `PushDialog(...)` 后会弹「自定义动作」选择框；不点它，fetch 永远不返回。补丁思路：**在 `PushDialog` 调用之后、原流程之前，插入一次 `DialogVM.Confirm()`**（`ldloc.0 → isinst → brfalse → castclass → callvirt Confirm`）。

```bash
# 探针前置（仅探针用，不进 A 链：它会改变所有 fetch 的交互行为）
dotnet /tmp/ca-patch/bin/Release/*/ca-patch.dll   "$APP/SourceTree.Api.UI.Wpf.dll"          # 打补丁
dotnet /tmp/ca-patch/bin/Release/*/ca-patch.dll   "$APP/SourceTree.Api.UI.Wpf.dll" --verify # 只校验
# 期望输出：PATCHED Fetch / PATCHED Pull / PATCHED Push；重复跑 ⇒ ALREADY <method>（幂等）
```

补丁器最小实现见 [profiles/CustomActionsPatch.cs](profiles/CustomActionsPatch.cs)（Cecil：定位 `PushDialog` 的 `callvirt`，在其后插 `Confirm()`；三个坑见文末）。

> 下面片段里的 `Prop`/`PropSet`/`Call` 是反射小工具，定义见同目录 [Helper.cs](profiles/Helper.cs)。

### ⑥-2 push：`Confirm()` 前填 4 个成员

```csharp
// tab = RepoTabViewModel；先调 tab.Push() 让对话框 VM 建好，再取 DialogContainer 里的 GitPushDialogViewModel
static void FillPush(object vm) {
    // 1) 远端名列表（空 ⇒ Confirm 时 IndexOutOfRange/什么都不做）
    var remoteNames = Prop(vm, "RemoteNameList");                    // IList<string>，数据源 RepoHandler.GetRemotes()
    remoteNames.GetType().GetMethod("Add").Invoke(remoteNames, new object[] { "origin" });
    PropSet(vm, "SelectedRemoteIndex", 0);
    // 2) 分支勾选表：每个条目 LocalBranch/RemoteBranch/Push
    var branches = Prop(vm, "Branches");                             // IList<PushBranchEntry>
    var et = branches.GetType().GetGenericArguments()[0];
    var entry = Activator.CreateInstance(et);
    et.GetProperty("LocalBranch").SetValue(entry, "master", null);
    et.GetProperty("RemoteBranch").SetValue(entry, "master", null);
    et.GetProperty("Push").SetValue(entry, true, null);
    branches.GetType().GetMethod("Add").Invoke(branches, new[] { entry });
}
```

### ⑥-3 pull：`Confirm()` 前填 4 个成员

```csharp
static void FillPull(object vm) {
    var remoteList = Prop(vm, "RemoteList");                         // IList<string>
    remoteList.GetType().GetMethod("Add").Invoke(remoteList, new object[] { "origin" });
    PropSet(vm, "SelectedRemote", "origin");
    var branchList = Prop(vm, "RemoteBranchList");                   // IList<string>
    branchList.GetType().GetMethod("Add").Invoke(branchList, new object[] { "master" });
    PropSet(vm, "SelectedRemoteBranch", "master");
}
```

调用顺序（三选一）：`tab.Fetch()` / `tab.Push()` / `tab.Pull()` → 下一 tick 取 `tab.DialogContainer.<DialogVM>` → `FillPush/FillPull` → `Confirm()`。**`Confirm` 是 `Family`(protected)**，跨程序集注入时要先把它改成 `public`（位掩码 `(attrs & ~MemberAccessMask) | Public`，否则 `MethodAccessException`）。

**进程外判据**（不要用 UI 反射值，K-1449）：

```bash
git -C /tmp/stgit rev-parse origin/master      # fetch 后应等于远端分支最新 hash
git -C <remote-repo> log --oneline -1          # push 后远端 HEAD 应含刚提交的 message
git -C /tmp/stgit rev-parse HEAD               # pull 后本地 HEAD 应追上远端
git -C /tmp/stgit status --short               # 三操作后都应为空
```

实测（K-1466/K-1467）：fetch 使 `origin/master` `387c805`→`fc5ca2b`；push 使远端 HEAD = `ecc27d5`；pull 使本地 HEAD = `81a750a`。

**不满足时的现象**：
- fetch 卡住不返回（对话框没被确认）⇒ 需 ⑥-1 的 IL 补丁；
- push/pull 抛 `NullReferenceException` / `ArgumentException`（集合为空，`Confirm` 内部索引越界）或静默什么都不做；
- 非快进时 push 报 `non-fast-forward`（**链路仍通**，是 git 语义拒绝，不是程序化失败；先 `fetch`+`merge`/`--force` 再推）。

## ⑦ 打开**新**仓库后让 UI 跟随（K-1481）

打开**新**仓库时，`AddOrActivate` 的 IL 有「索引没变就跳过 `set_SelectedTabIndex`」逻辑（`IL_0072~0081`：`SelectedTabIndex == IndexOf(tab)` 就 `ret`）。而它执行时 `Tabs` 里只有新仓库（索引 0）且 `_selectedTab` 恰好已是 0 ⇒ 跳过设置；**随后上次会话的旧 tab 恢复加入（索引 1）会把选中置成 1** ⇒ UI 停在旧仓库、新 tab 的 `LogRows` 恒 1。

**规则（顺序不能省）**：
1. `AddOrActivate(path, mode, null)`；
2. **等 `Tabs` 计数稳定**（旧会话 tab 会稍后恢复：先 1 后 2）；
3. `set_SelectedTabIndex(Tabs.IndexOf(目标仓库 tab))`。

**判据**：`SelectedRepoTabViewModel.Repo.Path` == 目标路径，且该 tab 的 `LogVM.LogRows` 数秒内 ≥2。

> ⚠️ K-1478/K-1479/K-1480 三轮「大仓库 History 不加载」都是这条规则没做导致的**误判**（读到的是旧仓库 tab 的 VM），不是性能问题、也不是回填断裂。实测（K-1481）：设索引后 `selIdx=0`、`selPath=/tmp/repo100`、`LogRows` **1→100**，3/3 复现。

### 别用 `pkill -f "…SourceTree"` 清进程（K-1472/K-1484/K-1489/K-1492）

`pkill -f "ldp/dotnet/dotnet .*SourceTree"` 会把**调用方自己的 shell** 一起杀掉（你的命令行里就含匹配串）。安全写法：

```bash
ps -eo pid,cmd | grep "ldp/dotnet/dotnet" | grep -v grep | awk '{print $1}' | while read p; do kill "$p"; done
```

## 附加：等待/事件相关（K-1441 / K-1444）

- `cmd\git.exe` 用**延迟退出 wrapper**（`/usr/bin/git "$@"` → `sleep 0.15` → `exit $rc`），否则出现 `"git status"失败 … the process has exited` 的竞态（K-1441/K-1442）；
- `WaitForMultipleObjectsEx` 在 shim 侧已是「最小降级」（`WAIT_TIMEOUT` + `usleep`），不再抛 `Win32Exception(50): No CSI structure`（K-1444）。
