## L-1 客户区渲染空白（客户区 4 色）

- **现象**：SourceTree 主窗口能创建（`WID=8388613`）、AT-SPI 可枚举，但客户区截图 **4 色 / 9172 字节**（空白）

- **根因（已精确到 C++ 内部，K-908/909/911/912）**：
  - ✅ 渲染引擎存在：`wpfgfx_cor3.so`（5086064 B，129 个 T 导出）
  - ✅ 传输建立成功：`WgxConnection_Create` 未抛异常（`MediaSystem.cs:200`）
  - ✅ **渲染策略开关已开**：`Switch.System.Windows.Media.ShouldRenderEvenWhenNoDisplayDevicesAreAvailable = true`（`runtimeconfig.json`）⇒ 实测 `MediaContext.get_ShouldRenderEvenWhenNoDisplayDevicesAreAvailable == True`
  - ✅ shim 的贴图路径已实现：`BitBlt` → `XCopyArea`（`win32_gdi_dc.c:364`）、`XPutImage`（`:412`）
  - ❌ **缺口**：`wpfgfx` **内部**的 `Present` 输出目标（`WgxConnection_SameThreadPresent` 只有导出、**无托管 DllImport** ⇒ `LD_PRELOAD` 也无法拦截）

## L-11 像素不可得是**架构性**的（K-1087）

> **⚠️ 已过时（2026-11-02 第 963 轮）**：K-1087 的「`wpfgfx_cor3.so` 无 Linux 后端」是**错判**。实测证明 `$FX/wpfgfx_cor3.so` 的 sha256 与仓库 `40-build/milcore-bridge` 构建产物**完全一致**（`cb1ad8f2…`），是**真正的 Linux 实现**（75 文件 / 27486 行 / SkiaSharp + `X11PresentationTarget` → `XPutImage`）。`nm -D` 无 GL/EGL 符号是因为它走**软件光栅 + `XPutImage`**，不需要 GL。真实原因见 K-1110：客户区空白是「`通道 3 无根视觉（未 TargetSetRoot）`」，修 `RepoTabPanel` 内容即解决。本条的「架构性不可达」结论**已被推翻**，保留作为历史记录。

> **2026-11-02**

**根本原因（实测）：**
```
nm -D wpfgfx_cor3.so | grep -ic "x11|drm|egl|vulkan|glx|opengl"  →  0
ldd wpfgfx_cor3.so | grep -i "X11|GL|EGL|drm"                     →  （无）
```

**⇒ `wpfgfx_cor3.so`（131 导出）**没有任何 Linux 图形后端符号或依赖** ⇒ 它是 **Windows 版二进制改扩展名**。**

**⇒ 因此：**
- **WPF 的**布局引擎**（`ActualWidth`/`ActualHeight`）在 Linux 上**工作**（140 控件 / 280 几何，K-1013）** ✅

- ⇒ **`GetName` 请求未到达 shim handler**，在 `dbus-daemon`/`libdbus` 层就被拒

**矛盾点（未解释）：**
- `gdbus introspect` 显示 `interface org.a11y.atspi.Action { methods: GetName(in i, out s) }` —— **XML 正确**
- 但 `gdbus call` / `dbus-send` 都返回 `UnknownMethod`

**⇒ 最终结论（K-1194，更精确）：**

**不是「`GetName` 特例」，而是**整个 `org.a11y.atspi.Action` 接口的**方法**全部被 `libatspi` 拒绝**（`GetActions` / `DoAction` / `GetName` 全 `UnknownMethod`），**但属性通道正常**（`Properties.Get("NActions")` → 1）。

**关键对比（K-1194 实测）：**
| 通道 | 状态 |
|---|---|
| `org.freedesktop.DBus.Properties.Get("NActions")` | ✅ **成功**（`nActions=1`）|
| `org.a11y.atspi.Accessible.GetRole` / `GetInterfaces` | ✅ **成功**（到达 handler）|
| **`org.a11y.atspi.Action.DoAction(0)`** | ❌ **`UnknownMethod`**（未到达 handler）|
| **`org.a11y.atspi.Action.GetName(0)`** | ❌ 同上 |

**⇒ 最可能的原因（K-1194）：`libatspi` 在**创建 `AtspiAction` 对象时**就固定了「可调用性」（基于当时的 `GetActions` 返回，空 ⇒ 不可调用）；之后 `NActions` 属性虽读到 1，但对象的可调用性缓存**不更新**。**

**⇒ 这是 `libatspi` 的内部实现限制，**不是 shim 能修的**（shim 的 `Introspect` 显示 7 个方法全在、`NActions=1` 也正确）。**

**⇒ 不影响其他成果**：`nActions=1` 已证明 `libatspi` 认出了 Action 接口（这是关键里程碑）。

**⇒ 后续可尝试**：
1. **重启 `dbus-daemon` / `at-spi-bus-launcher` 清缓存**
2. **查 `libdbus` 的 `dbus_message_iter` 参数类型检查（可能 `int32` vs `uint32`）**
3. **或改用 `DoAction` 直接触发（不需要 `GetName`）**

## L-17 合成输入通道（`WPF_FAKE_CLICK` / `WPF_FAKE_KEYS` / `xdotool`）均不可靠

> **2026-11-02（第 1036 轮）**

**现象：三条注入路径都无法稳定驱动 WPF 输入。**

| 通道 | 机制 | 实测结果 |
|---|---|---|
| `xdotool key/click` | X11 XSendEvent / XTEST | **完全无效**（K-1219/K-1220/K-1226；按键到达 shim 但 `WM_KEYDOWN` 未进被 pump 的队列）|
| `WPF_FAKE_CLICK` / `WPF_FAKE_KEYS` | `GetMessageW` 内 `wpf_queue_push` 直投 | **偶发有效**（K-1228 Tab×8 成功 -6351B），但**同参数重跑可能无变化或崩溃**（K-1230/K-1231）|

**根因（两条独立缺陷叠加）：**
1. **线程路由**：X 事件在 A 线程 pump，而消息按 `owner_thread` 投给 B 线程 ⇒ 进无人取的队列（K-1225）；三次修复均失败（投 owner/投 X 线程/投 `g_pump_thread`）。
2. **就绪竞态**：`FAKE_*` 用固定 3s 延迟，撞上不同的初始化阶段；改 `WM_PAINT>=3` 后崩溃率反而升到 2/3（K-1231）。

**⇒ 结论：在当前 shim 架构下，「外部/内部合成输入可靠驱动 UI」不可达。**
- **可用的替代**：进程内 API（Cecil 注入 + 反射 `InvokeProviderWrapper`），已达成（K-1143）；
- **不可用**：真实键盘/鼠标事件驱动、`pyatspi` 的 `DoAction`（L-15）。
