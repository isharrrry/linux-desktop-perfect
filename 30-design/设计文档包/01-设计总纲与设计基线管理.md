## 0. 本文件的作用

本文件是 LinuxDesktopPerfect 设计文档包的**总纲**，只回答六个问题：

1. 这套文档谁说了算、冲突时听谁的（§2、§3）。
2. 编号怎么分配、谁有权定义、怎么保证不悬空（§3）。
3. 每条需求、每个决策、每个风险、每张表、每条判据在哪份文件哪一节（§4）。
4. 设计基线怎么冻结、怎么变更、改完跑什么（§5）。
5. 设计依据与约束是什么、术语以哪份文件为准（§6）。
6. 文档与图表怎么规范、签署与归档怎么走（§7、§8）。

**两件本包特有的事**，先说清楚，避免误读：

- **判据先行**（ADR-014）：本包不只是「建什么」，还包括「凭什么说建成了」。测试门（TG-001~TG-015）与判据落点定义在 [《08-判据先行与界面检测设计说明》](08-判据先行与界面检测设计说明.md)，它不是验收附录，是设计的一部分——没有可执行判据的模块视为未设计。
- **无障碍优先**（ADR-015）：每个样本界面的**元素属性表**（角色/名称/状态/动作）定义在 [《界面设计说明》](界面设计说明.md)，它是界面的第一可机判据。后续自动检测界面时读这张表，不读截图。

## 2. 文档权威顺序（冲突时的裁决规则）

两份文件说法不一致时，按下表裁决，**上位覆盖下位**：

```text
1. 20-spec/需求与验收判据文档.md                ← 需求与验收的唯一事实源
2. 30-design/概要设计.md                        ← ADR / MOD / SYS / R 的唯一事实源
3. 30-design/设计文档包/04-接口设计说明.md       ← 字段级契约（IF）
4. 30-design/设计文档包/05-数据与清单设计说明.md ← 清单与表结构（TBL）
5. 30-design/设计文档包/06-安全性设计支撑材料.md ← 安全要求（SAFE）唯一正文
6. 30-design/设计文档包/界面设计说明.md          ← 界面元素属性表（SCR / GAP）
7. 30-design/设计文档包/08-判据先行与界面检测设计说明.md ← 测试门（TG）与判据落点
8. 30-design/设计文档包/03-软件设计说明.md        ← 实现细节与状态机（SM）
9. 30-design/设计文档包/02-系统-子系统设计说明.md ← 系统分解说明
10. 本文件、README-核心包                        ← 导航与索引，不承载规则
```

**四条硬规则**：

- **规则 A**：需求冲突以 `20-spec` 为准；设计不得自行扩大需求，也不得把没实现的条目写成「已支持」。
- **规则 B**：同一编号在两处定义不同内容时，以**定义方**为准（§3 的「定义方」列），引用方必须改成引用，不能各写一套。
- **规则 C**：任何文件不得引用 `90-archive/` 作为当前基线；归档只作历史证据。
- **规则 D**：判据冲突以 08 的测试门为准；08 与实现冲突时，红的是实现，不是判据——除非按 §5.3 走判据变更。

**编号纪律**：

1. 编号一经分配不得复用；删除的编号留空，并在 §5.5 变更记录里说明。
2. 一个编号只在一个文件里「定义」，其余文件只「引用」。定义方式：出现在定义方的编号小节标题或编号表格首列。
3. 引用格式统一为 `前缀-编号`（如 `REQ-FN-006`、`TG-003`），不加书名号、不加空格、不加行号。
4. 新增编号必须同时更新 [#设计模型](../model/model.json)；[#编号检查器](../checks/check-design-ids.mjs) 拿模型当期望，文档与模型不符即红。
5. 跨族引用要写成「族 + 编号 + 一句话」，不写「见上表」「同上」——Agent 改文档时没有「上表」。
6. **非受管标签**：`CSCI-*`、`S0~S7`、`B1~B10` 只是文档内的分组标签，不参与编号检查器、不进 [#设计模型](../model/model.json)；新增标签族先在[《术语表》](../../00-admin/术语表.md) §3 登记。

6. 影响哪些 `R`？是否要新增风险？
